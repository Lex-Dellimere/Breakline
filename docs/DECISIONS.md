# Decisions

Every decision and why. Newest at the bottom. Reference them as D1, D2, ...

## 2026-10-31 — phase 0

### D1. Poncho layout and app names
- **Decision:** `core/` is OTP app `:breakline` with modules `Breakline.*`. `cloud/` is `:cloud` with
  `Cloud.*` / `CloudWeb.*`. `gateway/` is `:gateway` with `Gateway.*`. cloud and gateway depend on
  core by path.
- **Why:** the brief names the core modules `Breakline.*` and the gateway ones `Gateway.*`. The
  supplied installer would have named the Phoenix app `breakline`, giving `Breakline.Repo` and
  friends. That would share a namespace with core and blur the boundary between the pure library
  and the web app.

### D2. Ash stack instead of plain phx.gen.auth
- **Decision:** cloud uses Ash 3 + AshPostgres + AshPhoenix + AshAuthentication (password strategy
  for login), ash_admin, live_debugger, ash_ai and usage_rules, as in the supplied install command.
- **Why:** the install command was supplied with the brief and supersedes the brief's
  `phx.gen.auth` line. Ash resources also give us policies and actions that fit tenant/site/approver
  authorisation.

### D3. Pin ash_authentication 5.0.0-rc.15 and ash_authentication_phoenix 3.0.0-rc.11
- **Decision:** use the 5.0 release candidates, pinned exactly.
- **Why:** the brief requires passkeys (wax_) and a TOTP fallback (nimble_totp). Stable 4.15.0 has
  neither. 5.0.0-rc.x ships native `webauthn`, `totp` and `recovery_code` strategies built on
  exactly those two libraries. `mix igniter.install` skips pre-releases unless pinned.
- **Cost:** release candidates can still change API before 5.0 final. Revisit when 5.0 ships.
- **Approved:** user, 2026-10-31.

### D4. UI is mishka_chelekom only
- **Decision:** product UI uses only components generated by mishka_chelekom (stable 0.0.10). We
  remove Phoenix 1.8's daisyUI (a mix dep in 1.8.16) and `core_components.ex`. Sign-in, register and
  reset are our own LiveViews built from mishka components, mounted via the router's `live_view:`
  option. ash_authentication_phoenix's built-in components are not rendered. heroicons stays
  because mishka's icon component uses it.
- **Exceptions:** ash_admin and live_debugger have their own UI and are mounted in dev only. They
  are developer tools, not product UI.
- **Why:** user instruction: "only use mishka_chelekom for ui and ux".
- **Note:** mishka_chelekom is 0.0.x and its changelog has breaking changes between minors.
  Components are generated into our repo (it is a dev-only dep), so upgrades are opt-in.

### D5. Don't pipe the installer; dev db on 5433, phoenix on 4010
- **Decision:** we read the ash-hq install script and ran its steps by hand (`igniter.new` without
  `--setup`). Postgres 17 runs in our own container `breakline-pg` on `127.0.0.1:5433`
  (`docker-compose.yml`). Phoenix dev runs on port 4010.
- **Why:** `--setup` would have run `ecto.create` against port 5432, which on this machine is
  another project's container. Port 4000 is also in use.

### D6. ash_ai without req_llm
- **Decision:** install ash_ai with `--no-req-llm`. Its dev MCP plug stays inside the endpoint's
  code-reloading block.
- **Why:** nothing in v1 calls an LLM. Not shipping an LLM client in a security product's runtime
  keeps the dependency surface smaller. We can add it if a feature ever needs it.

### D7. core is pure and carries its own tz database
- **Decision:** core depends on `tz` (bundled tzdata, compiled in, no updater process) and passes
  `Tz.TimeZoneDatabase` explicitly via `Breakline.time_zone_database/0`. It uses Elixir 1.18's
  built-in `JSON` rather than adding Jason. Canonical JSON for the audit chain will be our own small
  encoder that sorts keys.
- **Why:** core must behave the same on cloud and on an offline gateway. No global config, no
  runtime network.

### D8. Threat-feed and catalog sources (verified 2026-10-31)
- **LOLRMM** (github.com/magicsword-io/LOLRMM, Apache-2.0): seed for `Breakline.Catalog`.
  - Vendor a filtered snapshot of `https://lolrmm.io/api/rmm_tools.json` with attribution.
  - Honour `Detection: false`, drop the `user_managed` placeholder, and support mid-label wildcards
    (`relay-*.net.anydesk.com`).
  - It has domains and ports only: no CIDRs and no protocol.
  - Take Control coverage is thin in LOLRMM, so add domains from N-able's own docs.
- **CISA KEV** (CC0): primary advisory trigger.
  - Feed: `https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json`.
  - Match on trimmed, casefolded `vendorProject` / `product` (e.g. N-able appears as both
    `N-Central` and `N-central`).
- **ACSC** (CC BY 4.0, attribution required): secondary trigger.
  - Feeds: RSS only, `https://www.cyber.gov.au/rss/alerts` and `/rss/advisories`.
  - CVE IDs and products appear in free text only, sometimes formatted `CVE 2026 63077`.
  - Duplicate items appear under different links.
  - Needs HTTP/1.1.
  - It published the Aug 2026 N-central alert about 15 days after KEV listed it.
- **DoH lists:** the maintained lists (dibdot, hagezi) are GPL-3.0.
  - Fetch them at runtime rather than bundling them.
  - Final decision in phase 2/4.
- **Vendor IP ranges:** only Datto publishes current IPs (via DNS A records). Everyone else says
  their IPs change. Domain + resolved-IP blocking is the primary control, as the brief designs.

### D9. Firmware deferred to the last phase
- **Decision:** develop and pilot the gateway on a Linux host first. Nerves firmware comes last.
- **Why:** stock `nerves_system_x86_64` 1.35.x has no physical NIC drivers (virtio only) and
  carries OTP 29, while the host is on OTP 27. A 2-NIC mini PC needs a custom Nerves system. That
  shouldn't block the demo slice.

### D10. Commit and comment style
- **Decision:** commit messages and code comments are all lowercase, plain and human, with no emoji
  and no co-author trailers.
- **Why:** user instruction, 2026-10-31.

### D11. Auth page routing
- **Decision:** every page is one of our own mishka LiveViews in `cloud/lib/cloud_web/live/auth_live/`:
  - `/sign-in` via `sign_in_route live_view:`.
  - `/password-reset/:token` via `reset_route`.
  - `/confirm_new_user/:token` via `confirm_route`.
  - `/sign-out` via `sign_out_route`.
  - `/register` and `/reset` are plain `live` routes inside `ash_authentication_live_session` with
    `live_no_user`.
- **Why:** `sign_in_route` takes a single LiveView for sign-in, register and reset-request together.
  Splitting them keeps each page simple. The confirm and sign-out routes would otherwise render
  ash_authentication_phoenix's own UI, which breaks D4.
- **Removed:** `magic_sign_in_route` (there is no magic-link login strategy) and `auth_overrides.ex`.

### D12. Dev tool wiring
- **Decision:**
  - ash_admin's route lives only in the router's `dev_routes` block. The dep stays in all envs, as
    its installer added it.
  - live_debugger is a dev-only dep and runs on port 4017, because its default 4007 is taken on the
    dev machine.
  - `cloud/AGENTS.md` is synced by usage_rules, with ash packages linked rather than inlined.
  - phx.new's daisyUI and core_components guidance in `cloud/AGENTS.md` was rewritten to point at
    mishka.
- **Why:** keep product UI mishka-only (D4) and keep agent instructions consistent with it.
- **Revisit:** make ash_admin `only: :dev` once the router no longer needs it at compile time
  outside dev.

## 2026-10-31 — phase 1 (core)

### D13. Schedule semantics
- **Windows:** windows are local wall-clock times in the site's IANA zone. A recurring window with
  `ends <= starts` crosses midnight. `ends == starts` is invalid, so "all day" means two windows.
  Occurrences are half-open `[start, end)`.
- **Precedence:** active advisory lock > active break-glass > active window > locked. `mode` does
  not affect the schedule; the gateway decides whether to block or only log.
- **DST is fail-closed, giving the shortest real opening:**
  - a repeated (ambiguous) local start takes the later instant;
  - a repeated local end takes the earlier instant;
  - a skipped local time resolves to the transition instant;
  - an occurrence that becomes empty is skipped. Example: a window fully inside Sydney's repeated
    02:00–03:00 hour never opens.
  - Property tests prove that a window is never open when a naive wall-clock reading says closed.
    Away from transitions the two agree exactly.
- **Advisory locks** lock the whole site. The cloud only creates them for sites whose `tool_ids`
  include the matched tool.
- **`explain/2`** returns the reason as well as the state, for the dashboard. When several
  candidates apply:
  - several active locks: the first in policy order wins;
  - several active windows: the one ending last wins.
- **Why:** fail closed everywhere the brief allows it. The rare 2–3am DST-night window losing its
  repeated hour is an acceptable cost.

### D14. Policy wire format is strict
- `Policy.from_map/1` accepts only the exact form `to_map/1` emits and rejects unknown keys.
- Datetimes are UTC with whole seconds and a trailing `Z`; local times are whole minutes.
- A sub-second lock expiry rounds up; a sub-second break-glass end rounds down.
- **Why:** an older gateway must never silently drop a new restricting field. It rejects the
  policy and keeps enforcing the last good one.

### D15. Signed command details
- **Signed message:** canonical JSON of the envelope (`Breakline.CanonicalJSON`). It is not RFC 8785:
  floats are rejected and keys are sorted by utf-8 bytes, which only differs for characters
  outside the BMP.
- **Key rotation:** `key_id` sits inside the signed envelope.
- **Single spellings:** nonce and signature must be the canonical base64url spelling. Datetimes
  must be the exact UTC form. `expires_at` must be after `issued_at`.
- **Check order:** shape, key, signature, site, not-yet-valid (5 min skew), expired, ttl
  (max 24h), version, nonce.
  - An exact replay is therefore rejected as `:stale_version`.
  - The nonce cache only matters if the stored version is lost.
- **First version:** a fresh verifier starts at version 0, so the first policy is version 1.
- **Expiry** governs acceptance only. An accepted policy stays enforced after its command expires.

### D16. Audit chain details
- `hash = sha256(prev_hash_bytes <> canonical_json(entry + seq))`. The genesis `prev_hash` is 32
  zero bytes and `"seq"` is reserved.
- `verify_chain/2` detects edit, insert, delete and reorder inside the records it is given.
- Tail truncation, appended valid records and full re-hashing are only detected with
  `expected_head`, so the head must be anchored somewhere else (threat model T9).

### D17. Catalog curation
- **Contents:** 8 tools, sourced from a vendored LOLRMM snapshot of 14 slugs
  (`core/priv/catalog/lolrmm_snapshot.json`, Apache-2.0 with a NOTICE) plus vendor docs.
- **Curated list:** `core/priv/catalog/tools.json`. A provenance test checks that every LOLRMM
  domain and port exists in the snapshot.
- **Patterns:**
  - exact names;
  - `*.suffix`, which needs at least one label and never matches the bare suffix;
  - a mid-label `*`, which never crosses a dot.
  - `*.tld` is rejected. No two tools' patterns overlap.
- **Excluded on purpose** (each reason is recorded in tools.json):
  - `*.connectwise.com`: it covers PSA, Automate and portals.
  - `*.n-able.com` and `n-able.com`: they cover every N-able product. N-able-hosted N-central servers
    are added per site as `site_hosts`.
  - `*.system-monitor.com`: shared with N-sight.
  - Cove backup domains: blocking them would stop backups.
  - N-sight RMM domains: a separate product, not in the catalog.
- **TeamViewer ports:** 5938 tcp/udp and 80 come from TeamViewer's ports page, verified 2026-10-31.
- **KEV keys:** matched after trim, whitespace collapse and downcase. Single-product vendors
  (AnyDesk, TeamViewer, Splashtop, NinjaOne) use product `*`. The keys for take_control, datto_rmm
  and ninjaone are best guesses, because CISA has never listed them.
- **Known gaps:**
  - Datto RMM has only 3 domains. Datto's `*-ips.centrastage.net` A records could fill this in
    phase 2.
  - Shared ports (80/443) must only be dropped towards a tool's own IPs.

## 2026-10-31 — phase 2 (gateway)

### D18. Firewall ruleset
- **Table and transaction:** everything lives in `table inet breakline` and is applied as one
  atomic `nft -j -f` transaction.
- **Sets:**
  - The resolved-ip sets `rmm4`/`rmm6` are never flushed. Each element carries its own timeout of
    `clamp(dns ttl, 1h, 24h)`.
  - The static sets (`block*`, `doh*`) and both chains are rebuilt on every apply.
- **Always on:**
  - drop tcp/udp 853 (DoT/DoQ);
  - drop tcp/udp 443 to known DoH resolver ips;
  - redirect client :53 to the gateway resolver, on `lan_interfaces` only.
- **While locked:** drop everything to `@rmm*` and `@block*`, plus the exclusive ports to any
  destination.
- **Enforce mode** drops with no conntrack match, so live sessions are cut when a lock starts.
- **Monitor mode** (pilots):
  - the same rules become `ct state new` + counter + `limit 30/minute burst 10` + log, with no
    verdict;
  - counters therefore count connections, not packets;
  - logging is rate-limited, so a busy RMM session can't flood a pilot box's logs.
- **Validation:** the golden rulesets load into real nftables 1.1.3 in a throwaway container
  (`mix test --only nft_docker`). No traffic has been pushed through them yet (phase 6).

### D19. Catalog port scope
- `"any"` ports are dropped towards every destination while locked, which also stops direct P2P
  sessions: anydesk 6568/7070, teamviewer 5938 tcp+udp, take_control 3377, screenconnect 8041.
- Every other port is `"tool_ips"` and never dropped on its own.

### D20. DNS resolver behaviour
- **Order of checks:**
  1. DoH hostnames and canaries always get NXDOMAIN.
  2. Catalog names and exact site hostnames: NXDOMAIN plus a background shadow lookup (A and
     AAAA) when locked and enforcing; forwarded and logged as a would-block in monitor mode;
     forwarded when open.
  3. Everything else is forwarded unchanged, then its CNAME chain is checked, so a vanity name
     CNAMEd into a catalog domain is caught.
  - Resolved ips from 2 and 3 feed the firewall's resolved-ip sets.
- **NXDOMAIN carries no SOA,** so clients don't cache it and access returns as soon as a window
  opens.
- **Refused queries:** a query with zero or several questions gets FORMERR. Opcodes other than
  QUERY get NOTIMP. Neither is forwarded, since that would bypass the checks.
- **No snapshot from the enforcer** means the fail-closed default: locked, enforce, all catalog
  tools.
- **Ports:** dev listens on 127.0.0.1:5300 with upstreams 1.1.1.1/9.9.9.9. Production uses :53
  and configured upstreams.

### D21. DoH list is our own
- `gateway/priv/doh/resolvers.json` covers 6 providers (Cloudflare, Google, Quad9,
  OpenDNS/Cisco, AdGuard, NextDNS), each entry with the provider's own documentation URL.
  NextDNS publishes no ips, so it is blocked by name only.
- **Canaries** always get NXDOMAIN:
  - `use-application-dns.net`, which tells Firefox to disable DoH;
  - `mask.icloud.com` and `mask-h2.icloud.com`, which tell Apple to disable iCloud Private Relay.
- The GPL-3.0 community lists are still deferred: the cloud would fetch and push them in
  phase 4.

### D22. Enforcer semantics
- **Fail-closed states:**
  - With no policy (fresh install, or a tampered `command.json`) the gateway is locked, in
    `default_mode` (`:monitor` unless configured), with all catalog tools. A pilot box can't
    cut off an MSP before it is configured.
  - An unsynced clock (timedatectl) locks RMM. A missing timedatectl counts as unsynced unless
    `assume_clock_synced` is set.
- **Accepting a command:**
  - Verify, then require type `"policy"`, a payload that parses, and envelope site and version
    that match the payload.
  - Persist `command.json` and then `verifier.json` before applying.
  - A rejected command consumes neither its version nor its nonce.
- **Boot:**
  - Re-authenticate the persisted command (signature and site, not expiry).
  - The version floor is `max(verifier.json, persisted command)`, so losing `verifier.json`
    can't reopen replays.
- **Evaluation** runs every 15 s, at the schedule's next change, on policy change, and whenever
  the firewall server restarts. The firewall is touched only when the desired state changed.
- **Gateway audit chain** (`audit.jsonl`) records `enforcer_started`, `state_changed`,
  `policy_applied`, `command_rejected` and `audit_chain_reset`. A broken chain is moved aside
  and a new chain starts with a reset entry.
- **Events are in-memory only;** the audit chain is the durable record.
- **Dev inbox:** a polled `tmp/dev/inbox` stands in for the uplink until phase 3.

## 2026-11-01 — phase 3 (cloud, uplink, first end-to-end)

### D23. Cloud data model and tenancy
- **Resources:** Ash resources for tenants, memberships (`:admin` / `:approver`), sites, windows,
  advisory locks, break-glass, MSP contacts, append-only policy versions, gateway events and
  gateway audit records.
- **Tenant isolation:**
  - Tenant-scoped resources use attribute multitenancy plus a `TenantMember` policy check.
  - Composite `(id, tenant_id)` foreign keys stop a record pointing into another tenant.
  - `Site` is `global?`, so trusted server code can find it by gateway certificate. Actor reads
    without a tenant return nothing (tested).
- **Trusted paths:** they use `authorize?: false` explicitly. Policy publishing and the gateway
  channel are the only ones.
- **Tenant default:** `advisory_mode` is `:auto_lock`.

### D24. Publishing and delivery
- **Publishing:**
  - Every policy-changing action publishes inside its own transaction: lock the site row, bump
    `policy_version`, build `Breakline.Policy`, store exactly `to_map` output, broadcast after
    commit. "Approved but not published" can't happen. 12 concurrent publishes give versions
    1..12.
  - A new site doesn't publish; its first policy-changing action makes version 1.
  - One-off windows that ended more than a day ago are left out, so policies don't grow forever.
- **Delivery:**
  - Delivery always re-signs the latest version as a fresh command (10 min ttl, new nonce).
  - A gateway that was offline gets a valid command for the current version on join.
- **`Cloud.Signer` behaviour:** the file signer in dev uses the same key format as the gateway.
  Production replaces it with a KMS/HSM-backed signer.

### D25. Gateway endpoint and identity
- **Endpoint:** a separate Phoenix endpoint (`CloudWeb.GatewayEndpoint`, port 4011), https only,
  with `verify_peer` and `fail_if_no_peer_cert`. It serves only the gateway socket: no router,
  sessions or static files. Browsers never see a client-certificate prompt.
- **Client certificate:** Bandit delivers it as `connect_info.peer_data.ssl_cert`. TLS options
  live under `thousand_island_options: [transport_options: ...]`.
- **Gateway identity:** a gateway is identified by the sha256 fingerprint of its certificate DER,
  pinned on the site. The CN is informational. An unpinned fingerprint is refused, and a gateway
  can only join its own site's topic.
- **Dev PKI:** made with the openssl CLI (EC P-256, SHA-256), under git-ignored `priv/keys/`.
- **Hosting implication:** production hosting must terminate TLS in the app for port 4011. A
  TLS-terminating proxy in front would break mTLS. Decide at deploy time.

### D26. Uplink protocol and gateway audit anchoring
- **Channel:** `gateway:<site_id>`. Join carries last_version and the audit chain id and head.
  The reply carries server time, heartbeat interval, the cloud's audit ack and, when the gateway
  is behind, a signed policy.
- **Gateway pushes:**
  - `policy_result`.
  - `heartbeat` (every 30 s, plus straight after a pushed policy or any state change, so the UI
    is never a cycle behind).
  - `events` (at most 500, with ids for dedupe, at-least-once).
  - `audit` (at most 200).
- **Audit anchoring (T9):**
  - The cloud verifies each audit batch with `AuditLog.verify_segment/2` after its anchored head,
    stores it and anchors the new head.
  - A new chain id (a gateway chain reset) is recorded once as an `audit_chain_reset` event.
  - Gaps and forgeries get `chain_mismatch`.
  - A repeated `chain_mismatch` at the same seq makes the gateway back off (2 s doubling to
    5 min) instead of looping.
  - Verified end to end: gateway head, uplink ack and cloud anchor agree.
- **Uplink resilience:**
  - A crash loop cools off for 5 minutes, then the uplink restarts. It never touches the firewall
    or the enforcer, and never stays down until reboot.
  - Reconnect backoff is 1 s to 60 s with jitter.

### D27. Demo UI
- **Pages:** `/sites` and `/sites/:id`, mishka components only, scoped to the user's memberships.
  They show live state with a readable reason, gateway presence, published vs applied version and
  live events.
- **Demo actions** (open 15/30/60 min, lock now, unlock) need only a password session until
  phase 4 adds passkey approval (T5). The panel says so.
- **Demo password:** `mix cloud.dev.demo_password` sets the seeded demo user's password from
  `DEMO_PASSWORD` (dev only).

## 2026-11-01 — phase 4 (approvals, advisories, notifications)

### D28. Per-action passkey step-up
- **What a step-up is:** a `Cloud.Accounts.StepUp` row bound to the user, tenant, purpose, subject and a sha256 of the canonical action parameters. It lives 2 minutes, is single use, and is dead after one failed verification.
- **Verification:** a WebAuthn assertion via Wax: user verification required, origin and rp_id checked, sign count must move forward.
- **Enforcement:** `RequireStepUp` runs inside the action's transaction. It applies to `Window :approve`, `:create_approved` and `:open_now`, `BreakGlass :create`, `AdvisoryLock :lift`, `Access.unlock` and passkey removal.
- **Locking** never needs a step-up.
- **Why not a session flag:** we use this instead of the strategy's session-wide "recently verified" flag, because that flag would approve any action.
- **Unlock path:** unlock consumes one step-up and hands it to each lock it lifts. The receiving check re-reads the row and requires it to be verified, unfailed and consumed within the lifetime; a struct passed in context is never trusted.
- **Registration:** passkeys are registered through our own Wax ceremony. The strategy's add-credential routes are disabled, and adding a second passkey needs a step-up from an existing one.
- **TOTP:** a sign-in second factor only, rate limited and replay protected; it never approves. Recovery codes and a QR code are still missing (no eqrcode dependency).
- **Sessions:** only the allowlisted auth flows create one, and password reset or confirm never skips TOTP.

### D29. Per-tenant cloud audit chain
- **Mechanics:** `Cloud.Audit` appends a `Breakline.AuditLog` record in the same transaction as each security-relevant action, serialised by locking a per-tenant head row. `verify/1` checks the chain against that head.
- **Recorded actions:** window decisions, open, lock and unlock, advisory locks, break-glass, publishes, passkeys, TOTP, step-ups, request links and notification channels.
- **Limit:** the head is in the same database (T9).

### D30. Advisories
- **Polling:**
  - ash_oban scheduled actions poll KEV every 30 minutes and the ACSC alerts and advisories feeds at :05/:35 and :10/:40, so KEV runs first.
  - One `advisories` queue with concurrency 1. No Oban Pro.
  - Conditional GETs (304 verified live).
- **Baseline:** the first successful fetch of each feed records every entry and acts on nothing (verified: 1766 KEV entries, no locks).
- **KEV matches:** `auto_lock` tenants get an advisory lock (source `kev:<CVE>`, no expiry; an admin lifts it with a step-up), and `ask` tenants get a pending site advisory.
- **ACSC matches:** CVE-via-KEV or whole-word product name, always pending. This resolves the parked "auto-lock or ask" decision as **ask**.
- **Parsing:** ACSC is parsed with `:xmerl_sax_parser` with entities disallowed, and deduplicated by title slug.
- **Confirming:** an approver or admin confirms or dismisses a pending advisory. Closing access needs no step-up.

### D31. Notifications
- **Channels:** Slack, Teams (Workflows webhooks only, since O365 connectors were retired in May 2026), email, and SMS through a dev adapter (provider still to choose).
- **Targets:**
  - Encrypted at rest with AES-256-GCM.
  - The UI shows only the webhook host.
  - Allowed hosts are exact: `hooks.slack.com/services/…` and `*.environment.api.powerplatform.com/powerautomate/automations/direct/…`.
- **Messages:** one line plus a link to a page (`/advisories`, `/requests`, `/sites/:id`). Never a button, action or token. User-supplied names are reduced to plain text.
- **Fallback:** a tenant with no email channel emails its admins and approvers.
- **Delivery:** an Oban job per channel, 5 attempts with backoff, and a 4xx other than 408 or 429 is permanent.
- **Dispatcher:** a single-node subscriber. With several nodes, move to an outbox (enqueue in the producing transaction).

### D32. MSP request links and break-glass
- **Request links:**
  - A request link is an Ash actor whose only rights are `Window :request` and reading its own windows.
  - The token is 32 random bytes; only its sha256 is stored. Links are emailed, last 14 days and can be revoked.
  - Every bad token gets one generic invalid page.
- **Request caps** (in the resource, under a row lock):
  - at most 3 pending and 10 per 24 h per link;
  - at most 12 h long, start no more than 5 min in the past;
  - 30 token lookups per ip per 10 min.
- **Approving** a request needs a step-up. Rejecting needs none.
- **Break-glass** is capped at 4 hours in the resource and needs a step-up. Revoking needs none.
- **Known residual:** the token sits in the URL, so it reaches browser history (the request log line was fixed in D37).

### D33. Landing page animation (exception to D4)
- **What:** the landing page hero has one decorative `<canvas data-crawl aria-hidden=true>` animated by `assets/js/landing_crawl.js`, imported from app.js. It isn't a LiveView hook because `/` is a controller page.
- **Constraints:** non-interactive, landing page only, theme colours, a still frame under `prefers-reduced-motion`, and paused when hidden or off-screen. All text, buttons and layout stay mishka components.
- **Why:** user request (roadmap idea 4.2).

## 2026-11-01 — phase 5 (dashboard, timeline, audit export)

### D34. Dashboard and timeline
- **Home:** `/dashboard` is the signed-in home: sign in, the brand link and a signed-in visit to an auth page land there. `/sites` stays.
- **One tenant at a time:** `?tenant=<id>` picks one, the first by name is the default, like `/settings/notifications`. Counters are computed from the cards, so a heartbeat updates both. Offline means not joined right now (presence), independent of open or locked.
- **Upcoming windows** come from the latest published policy, not the window rows, expanded with `Schedule.windows_between/3` for 7 days and shown in the site's zone. It shows what the gateway will enforce, with the same fail-closed DST rules. An active advisory lock gets a note, since it wins over every window.
- **Timeline** is its own page (`/sites/:id/timeline`) so the site page stays short. It merges gateway events, cloud audit entries whose data has the site's `site_id` (minus `policy.published`, which the policy versions show with more detail), policy versions and notification deliveries (admins only, as the resource allows).
- **Paging:** a cursor on `{time, kind, id}`, descending, applied per source in the query, so pages never skip or repeat items that share a timestamp. Audit entries, policy versions and deliveries are ordered by `inserted_at`, gateway events by the gateway's `at`.
- **Actor emails** are read with `Cloud.Accounts.emails_by_id/1` (trusted), because users cannot read other users. Only ids taken from records the user was allowed to read are looked up. Every tenant-scoped read is as the user.

### D35. Audit export format (`breakline-audit-export/1`)
- **Top level:** `format`, `generated_at`, `tenant`, `period` (`[from, to)`, UTC), `exported_by` (id, email, role), `sites`, `coverage`, `verification`, `cloud_audit`, `gateway_audit`.
- **Verification** always covers each whole chain: the cloud chain with `Cloud.Audit.verify/1` against its stored head, each site's current gateway chain with `AuditLog.verify_chain/2` from seq 0 against the anchored head, plus the number of recorded chain resets. The head is read before the records and later records are left out, so counts and head describe one chain.
- **Records:** per chain, one contiguous run of seqs, from the first record whose `at` is at or after `from` to the last before `to`, with the chain head, the record just before the run (`previous_record`), `from_genesis` and `to_head`.
- **Offline verification** (`Breakline.AuditExport`, `mix breakline.audit.verify` in core): a run is verified with `verify_segment/2` from its previous record, anchored at that record's own `prev_hash`, so the previous record's hash and every link after it are checked. A run that claims `to_head` must end exactly at the head; a run that ends earlier cannot check the head. It proves the file is a consistent piece of a chain ending at the stated head, not that the head is genuine (T9).
- **Exports are audited:** the download records `audit.exported` with the period, site ids and actor, never the data. The `/audit` preview builds the same export but records nothing.
- **Access:** admins and approvers of the tenant. A non-member gets a 403, a bad period a 400.
- **Download:** `GET /audit/export.json` in its own `:browser_download` pipeline (session cookie, json accepted), pretty json with `format` first, `content-disposition: attachment; filename="breakline-audit-<slug>-<first day>-<last day>.json"`, `cache-control: no-store`.

### D38. PDF report with the Typst CLI
- **What:** `GET /audit/export.pdf` (same params and access as `export.json`) renders `Cloud.AuditExport.to_render_model/1` with Typst v0.15.1 (Apache-2.0), run as a separate OS process, never a NIF. A crash or hang of the renderer cannot take the VM down. The `/audit` button is live.
- **Install:** `mix cloud.typst.install` downloads the official static asset `typst-x86_64-unknown-linux-musl.tar.xz` of the v0.15.1 GitHub release with Req, checks its SHA-256 against the checksum pinned in `Cloud.Typst`, and extracts the binary to `priv/bin/typst` (git-ignored, 0755). Typst publishes no checksum file. The pinned value is the digest GitHub publishes for the release asset (`sha256:a6d077d0...`), and a fresh download matched it when it was pinned. The binary's own SHA-256 is pinned too, so the task can tell the pinned binary from another one; it replaces another one only with `--force`. `--archive PATH` installs from a downloaded copy, for offline builds. Config: `:cloud, :typst_path` (dev and test: `priv/bin/typst`; prod: `TYPST_PATH`, else the release's own `priv/bin/typst`). v0.15.1 is the latest 0.15.x (checked 2026-10-31); its notes list no security fix.
- **Untrusted text stays text:** audit details are attacker-influenced (site names, reasons, gateway entries). The template reads `data.json` with `json()` and places every value as a string. A string is always set as plain text, so `#read(..)`, `#import ..`, `*x*`, `$x$`, `@ref` or `]` print literally. Data is never written into Typst source and never `eval`ed. A test renders all of these, then checks the text with Typst's own HTML export and with `pdftotext`. A second test checks that the template contains no `eval`, `import`, `include`, `plugin` or `image`, and reads no file but `data.json`. Typst's `--deps` output confirms that only `audit.typ` and `data.json` are read.
- **Isolation:** each render runs in a fresh 0700 temp directory (removed afterwards, also on error) holding only `data.json` and the template. That directory is Typst's `--root`, and the package paths point into it. Typst gets `--ignore-system-fonts`, so only its embedded fonts are used: Libertinus Serif for text and DejaVu Sans Mono for hashes. The template imports no package, so Typst never fetches anything. A test renders the hostile model inside `unshare -rn` (no network namespace) to prove it.
- **Determinism:** `SOURCE_DATE_EPOCH` is the export's `generated_at`, used as the document date, so the same export gives byte-identical PDFs (tested). Different exports differ.
- **Caps:** more than 20,000 records (`:cloud, :audit_pdf_max_records`) is refused before Typst runs. The download gets a 422 asking for a shorter period, and `/audit` shows the PDF button disabled with the same note. The json export has no cap. Typst runs under coreutils `timeout -k 5 60`, so it gets TERM at 60 s and KILL 5 s later; the download then gets a 503. A failed or timed-out render records nothing, and the export is recorded (`audit.exported`, format `"pdf"`) only once the PDF exists. The json export keeps format `breakline-audit-export/1` in its entry.
- **Layout:** A4. A header with "Breakline audit export", the tenant and the period, and a footer with "Page X of Y". The cover shows tenant, period, exporter, generation time, one large box per chain (intact or broken, with the head hash) and the scope note. From page 2 there is one table per chain (seq, time, actor, action, details, hash) with a repeating header. Details are the entry's other fields as `key: value`, shortened past 400 characters (the json has them in full).
- **Residual:** the timeout bounds a render that is already running, but a request that dies mid-render leaves `timeout` to finish its 60 s. Text in scripts that Libertinus Serif doesn't cover (CJK, for example) falls back to the other embedded fonts and may show missing glyphs.

### D41. Gateway enrolment replaces the gateway client CA
- **Identity:** still the sha256 of the gateway certificate's DER, pinned on the site (D25). The certificate is now self-signed (EC P-256, valid to 9999-12-31), made on the box by `Breakline.GatewayIdentity` with OTP `:public_key` only. No CA signs gateway certificates, so there is no client CA key to steal; unpinning a box revokes it.
- **Port 4011:** asks for a client certificate and accepts a self-signed one (`CloudWeb.GatewayTLS.verify_client/3`). OTP still checks the certificate's signature and dates (an expired one fails the handshake, tested), and CertificateVerify proves the client holds the key. An unpinned certificate can do one thing, `POST /gateway/enroll`; the socket refuses it.
- **Codes:** 160 bits, shown once as 8 groups of 4 base32 characters. Only the sha256 is stored. Valid 30 minutes, single use, cancellable, and a new code cancels the site's pending one. Issuing one needs the admin role and a passkey step-up with purpose `:enroll_gateway` bound to the site. Issue, use and cancel are audited, and the use entry carries the new and replaced fingerprints and the ip. Bad, used, cancelled and expired codes get one identical 403. Rate limit: 20 tries per ip per 10 minutes.
- **The box trusts the cloud through a pin, not a CA file:** the enrol command carries `--ca-sha256`, the sha256 of the 4011 CA's SubjectPublicKeyInfo (kubeadm's discovery hash). The box connects with `cacerts: []` and a `partial_chain` that accepts only the chain certificate with that hash, checks the host name, and checks the CA pem in the answer against the pin before writing `server_ca.pem`.
- **The pin comes from the TLS session,** never from the request body. A certificate pinned on another site gets a 409. Re-enrolling moves the pin and disconnects the old box's socket.
- **Why a plug route and not a socket topic:** the socket stays pinned-only, an unpinned box gets one request and one answer, and it works under `bin/gateway eval`, where slipstream isn't started.
- **Gateway config:** with `BREAKLINE_SITE_ID` set, the environment alone configures the box, as before. Otherwise `enrollment.json`, `server_ca.pem` and `identity/` do, and any variable that is set wins. An unenrolled box boots without raising: no site, no trusted key and no uplink, so it stays locked. The default data dir is `/var/lib/breakline`.
- **Cloud prod env:** `GATEWAY_CLIENT_CA` is replaced by `GATEWAY_TLS_CA` (the server's own CA) and `GATEWAY_URL` (shown in the enrol command), with optional `GATEWAY_SERVER_NAME`. `SIGNER_KEY_PATH` is now required in prod; before, prod silently used a build-time path.

### D43. Real traffic tests, and what they changed
- **Suite:** `mix test --only traffic` (22 tests, about 2 minutes) runs the prod release in throwaway `debian:trixie-slim` containers. Each has a client namespace (the clinic pc), the gateway in the container's own namespace, and an upstream namespace (the fake internet: dnsmasq, a rogue resolver, listeners on the RMM ports). There are two topologies: router, and transparent bridge (`br0`, with and without br_netfilter). Containers get NET_ADMIN and SYS_ADMIN (for `unshare`/`nsenter`) and nothing else, and never use host networking.
- **Proved with packets:** client DNS to any resolver (v4, v6, udp, tcp) is answered by the gateway. While locked, catalog names and CNAMEs into them get NXDOMAIN, and RMM ips, tool-only ports (AnyDesk 6568, TeamViewer 5938 tcp and udp), DoT and DoH are dropped while web traffic passes. While open everything RMM passes, and a lock or a window end cuts live sessions within 3 s. Monitor mode drops nothing and counts new connections. All of it holds over IPv6 too.
- **Bugs found and fixed:**
  - The prod resolver bound `0.0.0.0`, so the v6 redirect found no listener and v6 clients lost DNS. It now binds `::` (dual-stack) by default.
  - The resolver answered on every interface. An `input` chain now drops the resolver port unless it arrives on `lo` or a LAN interface.
  - A `flush ruleset` (Debian's stock `nftables.service`) removed the table for good. Every evaluation (15 s tick) now checks that `table inet breakline` is there and applies it again if not.
- **The kernel closes a window on time:** an open state carries `locks_at`, from the new `Breakline.Schedule.next_lock/2` (the first instant the policy locks again, following break-glass and windows, within the 14-day horizon). The ruleset loads the lock rules behind `meta time >= locks_at`, in unix seconds (kernel 5.4+, nft 1.1.3). If the BEAM dies mid-window, the window still ends on time: tested by SIGKILL before the end, with sessions cut within 3 s of it. While the BEAM is up, the enforcer swaps in plain locked rules at the end in one transaction, which leaves no gap. An open state with no end inside the horizon gets no guard.
- **Bridge mode is inet-family plus br_netfilter:** `bridge-nf-call-iptables` and `-ip6tables` must be 1, and the LAN interface must be the bridge (`br0`), because under br_netfilter the inet hooks see the bridge, never the port. Naming a port, or leaving br_netfilter off, fails open silently. `NftImpl` detects both and reports them in `Enforcer.status().firewall.host_problems`. A native bridge-family ruleset is deferred: it needs `nf_tables_bridge`, which the tests must not load on the host kernel.
- **Unit:** `StartLimitIntervalSec=0`, so systemd never stops restarting a crash-looping gateway.
- **Not verified:** monitor-mode log lines and their rate limit, because the kernel doesn't log from a non-init namespace. They are asserted through counters and the rule listing.

### D47. An N-central advisory also closes Take Control
- **What:** `take_control` carries the KEV key `n-able / n-central` as well as its own, so a KEV record for N-central closes both tools.
- **Why:** the N-central console launches Take Control sessions, and that is how the August 2026 attackers reached client machines (iTnews, 20 Aug 2026). - **How fast the KEV trigger would have been in August 2026** (CISA's own catalogue entries, `docs/research/buyers-and-channels.md` §5.1): exploitation was seen from 1 Aug. KEV listed CVE-2026-18577 on 3 Aug and CVE-2026-18556 on 4 Aug, and the ACSC High Alert went out on 19 Aug. So a KEV-triggered lock would have come about 2 days after exploitation began, and an ACSC-only trigger about 18 days after. CVE-2026-86218 (the September pre-auth RCE) was listed on 8 Sep, 3 days after Hotfix 4. The first 2 days stay uncovered, which is why closed-by-default matters more than the auto-lock.
