# Decisions

Every decision and why. Newest at the bottom. Reference them as D1, D2, ...

## 2026-10-31 — phase 0

### D1. Poncho layout and app names
- **Decision:** `core/` is OTP app `:breakline` with modules `Breakline.*`. `cloud/` is `:cloud` with
  `Cloud.*` / `CloudWeb.*`. `gateway/` is `:gateway` with `Gateway.*`. cloud and gateway depend on
  core by path.
- **Why:** the brief names the core modules `Breakline.*` and the gateway ones `Gateway.*`. The
  supplied installer would have named the Phoenix app `breakline`, giving `Breakline.Repo` and
  friends. That would share a namespace with core and blur the boundary between the pure library
  and the web app.

### D2. Ash stack instead of plain phx.gen.auth
- **Decision:** cloud uses Ash 3 + AshPostgres + AshPhoenix + AshAuthentication (password strategy
  for login), ash_admin, live_debugger, ash_ai and usage_rules, as in the supplied install command.
- **Why:** the install command was supplied with the brief and supersedes the brief's
  `phx.gen.auth` line. Ash resources also give us policies and actions that fit tenant/site/approver
  authorisation.

### D3. Pin ash_authentication 5.0.0-rc.15 and ash_authentication_phoenix 3.0.0-rc.11
- **Decision:** use the 5.0 release candidates, pinned exactly.
- **Why:** the brief requires passkeys (wax_) and a TOTP fallback (nimble_totp). Stable 4.15.0 has
  neither. 5.0.0-rc.x ships native `webauthn`, `totp` and `recovery_code` strategies built on
  exactly those two libraries. `mix igniter.install` skips pre-releases unless pinned.
- **Cost:** release candidates can still change API before 5.0 final. Revisit when 5.0 ships.
- **Approved:** user, 2026-10-31.

### D4. UI is mishka_chelekom only
- **Decision:** product UI uses only components generated by mishka_chelekom (stable 0.0.10). We
  remove Phoenix 1.8's daisyUI (a mix dep in 1.8.16) and `core_components.ex`. Sign-in, register and
  reset are our own LiveViews built from mishka components, mounted via the router's `live_view:`
  option. ash_authentication_phoenix's built-in components are not rendered. heroicons stays
  because mishka's icon component uses it.
- **Exceptions:** ash_admin and live_debugger have their own UI and are mounted in dev only. They
  are developer tools, not product UI.
- **Why:** user instruction: "only use mishka_chelekom for ui and ux".
- **Note:** mishka_chelekom is 0.0.x and its changelog has breaking changes between minors.
  Components are generated into our repo (it is a dev-only dep), so upgrades are opt-in.

### D5. Don't pipe the installer; dev db on 5433, phoenix on 4010
- **Decision:** we read the ash-hq install script and ran its steps by hand (`igniter.new` without
  `--setup`). Postgres 17 runs in our own container `breakline-pg` on `127.0.0.1:5433`
  (`docker-compose.yml`). Phoenix dev runs on port 4010.
- **Why:** `--setup` would have run `ecto.create` against port 5432, which on this machine is
  another project's container. Port 4000 is also in use.

### D6. ash_ai without req_llm
- **Decision:** install ash_ai with `--no-req-llm`. Its dev MCP plug stays inside the endpoint's
  code-reloading block.
- **Why:** nothing in v1 calls an LLM. Not shipping an LLM client in a security product's runtime
  keeps the dependency surface smaller. We can add it if a feature ever needs it.

### D7. core is pure and carries its own tz database
- **Decision:** core depends on `tz` (bundled tzdata, compiled in, no updater process) and passes
  `Tz.TimeZoneDatabase` explicitly via `Breakline.time_zone_database/0`. It uses Elixir 1.18's
  built-in `JSON` rather than adding Jason. Canonical JSON for the audit chain will be our own small
  encoder that sorts keys.
- **Why:** core must behave the same on cloud and on an offline gateway. No global config, no
  runtime network.

### D8. Threat-feed and catalog sources (verified 2026-10-31)
- **LOLRMM** (github.com/magicsword-io/LOLRMM, Apache-2.0): seed for `Breakline.Catalog`.
  - Vendor a filtered snapshot of `https://lolrmm.io/api/rmm_tools.json` with attribution.
  - Honour `Detection: false`, drop the `user_managed` placeholder, and support mid-label wildcards
    (`relay-*.net.anydesk.com`).
  - It has domains and ports only: no CIDRs and no protocol.
  - Take Control coverage is thin in LOLRMM, so add domains from N-able's own docs.
- **CISA KEV** (CC0): primary advisory trigger.
  - Feed: `https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json`.
  - Match on trimmed, casefolded `vendorProject` / `product` (e.g. N-able appears as both
    `N-Central` and `N-central`).
- **ACSC** (CC BY 4.0, attribution required): secondary trigger.
  - Feeds: RSS only, `https://www.cyber.gov.au/rss/alerts` and `/rss/advisories`.
  - CVE IDs and products appear in free text only, sometimes formatted `CVE 2026 63077`.
  - Duplicate items appear under different links.
  - Needs HTTP/1.1.
  - It published the Aug 2026 N-central alert about 15 days after KEV listed it.
- **DoH lists:** the maintained lists (dibdot, hagezi) are GPL-3.0.
  - Fetch them at runtime rather than bundling them.
  - Final decision in phase 2/4.
- **Vendor IP ranges:** only Datto publishes current IPs (via DNS A records). Everyone else says
  their IPs change. Domain + resolved-IP blocking is the primary control, as the brief designs.

### D9. Firmware deferred to the last phase
- **Decision:** develop and pilot the gateway on a Linux host first. Nerves firmware comes last.
- **Why:** stock `nerves_system_x86_64` 1.35.x has no physical NIC drivers (virtio only) and
  carries OTP 29, while the host is on OTP 27. A 2-NIC mini PC needs a custom Nerves system. That
  shouldn't block the demo slice.

### D10. Commit and comment style
- **Decision:** commit messages and code comments are all lowercase, plain and human, with no emoji
  and no co-author trailers.
- **Why:** user instruction, 2026-10-31.
